## Analyze

What the numbers show:

- **The seed is the whole run.** The same seed reproduced the same trace hash in every replay,
  and the totals of both 1,000-seed sweeps are the same on every rerun. A failure seen once can be
  rerun as often as needed, with a trace file (`dst run -seed N -bug -trace FILE`) for debugging.
- **The bug needs a particular message order.** 71.2% of seeds pass even with the bug: it shows
  only when a replication message is dropped or overtaken by a later one. On a real network such a
  bug would appear rarely and not on demand; in the simulator it appears in 288 known seeds.
- **Reads did not catch it; replica comparison did.** Clients read from the primary, so every read
  was correct in both sweeps. The bug was found only by comparing each backup with the primary at
  the end of the run. A store that served reads from backups would have exposed it as stale reads.
- **Idle time is free.** About 2.3 s of virtual time per seed (timeouts, retries, latency) runs in
  about 2 ms of wall time, because the clock jumps from event to event.

Root cause of the seeded defect (deliberate, `ArrivalOrderBug`): a backup applies each write when
it first arrives and acknowledges the highest sequence it has seen. Two mechanisms follow:

1. A write delayed past a later write to the same key is applied last, so the older value wins
   (stale value).
2. When a write is lost and a later one arrives, the backup acknowledges past the gap. The primary
   counts the lost write as acknowledged and never resends it (missing key when it was the key's
   only write, stale value otherwise).

The 8 "missing key" seeds can only come from mechanism 2. The 280 stale-value seeds can come from
either; the M1 trace records events, not message contents, so it does not separate them. The
correct backup buffers out-of-order writes and acknowledges only the highest contiguous sequence,
which removes both mechanisms (0 of 1,000 seeds failed).
